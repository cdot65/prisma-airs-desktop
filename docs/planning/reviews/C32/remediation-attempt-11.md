| Finding | Remediation | Where |
|---|---|---|
| R1 a count baseline that the transcript's eviction invalidates | An unconfirmed send and a competing send's claim record the IDs of the operator messages the conversation showed when it was sent, never a count: a message settles a record only if its ID was not shown then. The core numbers a conversation's messages (`u-{n}`) and drops its oldest entries past 200 entries or 1 MiB, so a position or count shifts while an ID does not; one-entry/one-attempt matching, exclusion of older identical messages, conversation isolation, claims (pending, confirmed, released) and remounts are unchanged. The core now also numbers a restored conversation's new messages past every `u-{n}` it shows (`harness::messages_after`), so a transcript saved after eviction can never get a message whose ID it already shows. Tests: "settles an unconfirmed send once its entry appears even when the transcript is at its 200-entry bound…", "…at its 1 MiB bound…" and "an admitted retry claims its own entry at the transcript bound too…" (each with a remount; all three fail against the count baseline), and the unit test `a_restored_transcript_continues_past_every_message_it_shows` | `store.ts`, `harness.tsx`, `harness.rs`, `harness_domain.rs`, provenance P50 |

Attempt-11's check run kept two core-fixture flake logs, each a timing-sensitive test outside C32 (transport connection release, an expired refresh read); the same-input rerun passed.

B1/E1 (the C29 live Vulture verification receipt) stay owner-gated (`evidence/C29/live-scope-request.md`).

The first attempt-12 check run failed in `harness_tools::a_tool_call_under_way_when_its_turn_is_stopped_is_never_answered` (a file C32 changes). Its cause was in the test, not the product: the slow read was a `thread::sleep` inside the synthetic plane's hook, which blocks a runtime worker (and with it the test's own timers), and the test waited for the read to be recorded, which happens only once it is answered, so under load the stop could land after the read. The read is now held by a gate under `tokio::task::block_in_place` until the stop has landed, and the test waits for the read to start (a flag set in the hook), then releases it and waits until it is served before asserting that nothing reaches the engine. It now passes in about 5 seconds instead of sleeping 13; the whole `harness_tools` target passed twice. The native record is unaffected (no product source changed; the executable hash is the same).
