# UI v2 "Refined Native" — design specification

Status: C27 deliverable, reviewed at the 9/10 bar (D058). This document and
its companions ([tokens](tokens.md), [state ownership](state-ownership.md),
[invariants](invariants.md), [screens](screens/), [provenance](provenance.md))
are what every P09 chunk is judged against. The existing
[DESIGN.md](../DESIGN.md) remains authoritative for the native authority
interface, transport, Academy presentation ownership and the Harness; this
document changes only how the desktop presents those.

## 1. Scope and deliverable

The reviewed prototype is extracted in three layers, in order:

1. **Spec** (C27, this folder): tokens, screen inventory, state ownership,
   invariants, interaction contracts, copy, provenance, acceptance criteria.
2. **TypeScript presentation** (C28–C29, then per-destination chunks): the new
   shell and screens in `apps/desktop`, built against wire fixtures and the
   mock runtime, behind a Rust-owned `ui_variant` flag.
3. **Rust contract** (within each destination chunk): the intents, scopes and
   refusals the screens need, implemented over existing desktop-core services
   and exported through ts-rs.

The first implementation slice is the shell plus the first-run wizard and
add-tenant sheet (C28–C29). Harness, Inbox/reads, reviews/Administration, API
Client, Test Cases and the Academy embed follow (C30–C34). The legacy shell,
its feature-view switch, the flag and the legacy native acceptance scripts are
removed in C34; the phase is not complete while any destination renders only
in the legacy shell.

## 3. Architecture fit

- **Authority** stays with desktop-core (D014). The UI dispatches intents and
  observes scopes through the existing two-command Tauri bridge. Every
  prototype state field is assigned in [state-ownership.md](state-ownership.md);
  no persisted or tenant-sensitive state is UI-owned (UI state is transient
  presentation state only), and no state goes to browser storage.
- **Contract**: new intents, scopes and refusals are Rust types with ts-rs
  derives, regenerated by `xtask bindings`. A hand-written parser is added to
  the contracts client only where runtime validation beyond the type is needed.
- **Shell flag**: `ShellSnapshot.ui_variant` (`legacy` | `v2`) and
  `ShellSnapshot.onboarding` (`needed` | `inProgress` | `done`) are Rust-owned,
  fixture-able and seedable by native acceptance. The React root switches on
  them.
- **Navigation inventory**: one Rust list (feature ids with availability,
  label, shortcut index and sidebar membership) feeds the native menu, the
  sidebar and the command palette. Feature ids gain `home` and `inbox`;
  `library` is shown as "Test Cases"; `gateway` and `redTeam` render inside
  Administration's accordion; `sessions`, `import` and `settings` stay
  reachable from the palette and Administration.
- **Shortcuts** ⌘1–⌘9 are defined by the native menu, which dispatches
  `navigate`; the sidebar displays the menu's truth.
- **Transient state**: a small zustand store per screen family (shell, wizard,
  inbox, admin, harness, workbench); React state only for form fields.
- **Tokens**: local `--v2-*` custom properties ([tokens.md](tokens.md));
  Academy variables untouched for the embedded learner view.
- **Copy**: one `copy.ts` per screen family exporting constants; tests assert
  exact strings. The voice is the wizard's: this app is built entirely on
  Palo Alto Networks' public APIs and exists to show application builders what
  those interfaces make possible; it explains the API call as you go.
- **Show the calls**: a Rust-owned preference reveals, for each action, the
  request and response as the diagnostics module already redacts them
  (credential ids in place of secrets, a note that the core attaches the real
  header). Default on until onboarding completes.

## 4. Layout rhythm

Shared by every destination, the wizard and the add-tenant sheet:

- 32px top and 44px side page margins; 26px/700 titles; 18–20px card
  padding; 10–12px gaps; 32px controls; 14px body, 12px secondary (11px only
  pills, eyebrows and mono badges); 860px reading cap; 244px rail (first-run
  wizard rail 320px).
- Minimum window 1180×720. Below 1280 wide the rail collapses to icons with
  tooltips; nothing scrolls horizontally.
- Tool workspaces (Harness, API Client) have a title row like every other
  destination; no destination is exempt from the rhythm.

## 6. Products, admitted services and the unsupported boundary

The prototype shows six products. Only a product with an admitted service in
desktop-core is verified, inventoried or changed; the rest render as
unavailable. Nothing in P09 adds a product API.

| Product | Admitted reads | Admitted changes | P09 treatment |
|---|---|---|---|
| AI Runtime Security | `ManagementResource` (profiles, topics, applications, API keys, deployment profiles, DLP catalog/profiles/patterns, filtering profiles, dictionaries, sessions); scan (`scan.rs`) | `ChangeKind` Profiles, Topics, Applications, ApiKeys, DataPatterns, DataProfiles, FilteringProfiles, Dictionaries with `ChangeAction` Create/Version/Rotate/Delete/… (`changes.rs`) | Full: Administration tabs, reviews, Playground, Inbox items |
| AI Gateway | `GatewayRead` (inventory, detail, integration models, prerequisites, observe, MCP servers) | Gateway `ChangeKind`s (workspaces, providers, routes, guardrails, service/user keys, integrations) | Full, inside Administration; Harness lifecycle 2 reads `McpServers` |
| AI Red Teaming | `red_team.rs` reads (scan inventory, statistics, static reports; C13) | none (execution stays a disabled preview) | Read-only card and tabs; Test Cases "Inspect" only |
| Model/skill observability (AI Supply Chain in the prototype) | C13 model/skill reads | none | Read-only; shown under its C13 name, never as a scanning product |
| Agentic Identity Security | none | none | **Not available in this release**: card and accordion entry with the dependency gate ("needs an admitted AIS service; see D058"); not selectable in the wizard; never verified; no inventory, no policy review |
| Agentic Endpoint Security | none | none | Same as AIS; the prototype's AES policy review, discovered-AI table and warning demo are fixtures only and are not implemented |

The per-tab and per-action mapping, including the restricted Runtime and
Gateway change matrices (for example no application Create, no API-key
Update, no data-profile Delete) and every removed or unavailable prototype
tab, is enumerated in
[screens/administration-inventory.md](screens/administration-inventory.md).

Rules: an unavailable product or tab never produces a verification result, an
Inbox item, an inventory row or a review. The wizard's verify step lists it
as "Not available" (not pass, warning or fail). Test V2-T19 asserts that the
admin inventory for an unavailable product has no tabs and no actions, and
V2-R10 asserts that no intent exists that would mutate it; V2-T20 and V2-R11
cover unavailable tabs and denied actions within admitted products.

## 7. Error presentation

- **Refusal** (core refused an intent): warn toast with the refusal reason and
  the tenant named; never a modal. Guard-type refusals (tenant switch with a
  pending decision) render their dialog from the refusal payload.
- **Delivery unknown**: inline "not confirmed" state on the control that
  dispatched, with Retry; the control is not reset.
- **Contract violation**: generic warn toast; detail to diagnostics.

## 8. Accessibility additions

The native acceptance checklist gains four items that every P09 chunk's
acceptance script asserts: accent-colour focus ring on every focusable
control (inset variant where declared); `role="status"` live regions for read
status, API send completion and review apply; one topmost modal with
`aria-hidden` siblings and focus return; toasts persist under Reduce Motion.
Existing requirements (keyboard-only, VoiceOver attributes, 150%/200% zoom,
contrast AA) continue to apply to every changed screen.

## 9. Budgets

Existing `budgets.json` entries carry unchanged. New: a tenant switch renders
the new tenant's Home from cached scopes within 100 ms, with read status
showing pending until the read lands (measured by the C30 workload).

## 10. Known gaps carried from the prototype

Codex round 16 (score 8) left five items, closed by the chunk named:

1. Secret disclosure survives a tenant switch with the key review open → I6, C31.
2. Applied injection-override examples show "Not demonstrated" → topic
   verdicts keyed separately from detectors, profile-aware, C31.
3. Administration creation labels from a per-product single value → per-tab
   `AdminInventory` capability and label, C31.
4. Home snooze tooltip hard-codes "Snooze 24 hours" → shared item
   `snoozeLabel`, I11, C30.
5. API Client Send announces nothing → `role="status"` completion region, C33.

## 11. Verification

- Behaviour: Vitest + Testing Library component tests, one named fixture per
  prototype wrapper board; the board → initial props → test id table is in
  [screens/boards.md](screens/boards.md), so reviewed-state coverage can be
  audited without reconstructing canvas wrappers.
- Contract: Rust integration tests per invariant (`V2-Rxx`).
- Native: the existing Accessibility-API scripts, extended per chunk, plus a
  screenshot evidence set per chunk at 100% and 200% zoom in both themes filed
  under `evidence/Cxx/screens/`.
- Live: only C29 (wizard verify against Vulture, reads only) and C31 (review
  apply against Redtail under the `airs-v2-c25-` prefix) run live, inside the
  scope the owner designated on 2026-10-25. Every other chunk runs on fixtures
  and the mock runtime.
- Review: C27 at 9/10 in every dimension, enforced by the controller (a
  `docs_only` chunk refuses owner acceptance and needs no native
  preparation); C28–C34 may complete at 8 under D034 and are raised to 9
  before the P09 phase review.
- Legacy native scripts removed in C34 are first mapped, assertion by
  assertion, to replacement native-check ids (C34 milestone 2), so the
  cumulative P09 gate keeps exercising every earlier authority and
  accessibility requirement.
