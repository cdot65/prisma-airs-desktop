# Provenance and intentional deviations

Every fixture file and screen contract cites the frozen prototype file and the
prototype state names it derives from. This file lists where the
implementation deliberately differs from the prototype and why. Anything not
listed here is expected to match the prototype's behaviour and spacing.

Frozen reference: canvas https://claude.ai/artifact/2SEXT1XMHdZkxHvdw8oaYL,
page "Refined Native v2", version 134 (version id 1793059808-4929, published
2026-10-26). Files and hashes: [prototype/MANIFEST.sha256](prototype/MANIFEST.sha256).

| P33 | `ReadStatus` as its own core scope with per-product states from dedicated reads | `readTenant` admits one finite read per chosen product through the existing management pipeline: the Runtime overview the shell already owns (sessions chart, key inventory, the chosen Gateway workspace's usage and limits), the Red Team statistics and scan list (C13's read), the model scans, skill statistics and skill scans (C13's read); each settles into the tenant's read record as a per-source outcome (read, needs a role, failed); a source counts as read only when it established what it is for: a listing whose page is the inventory (not capped, nothing beyond the first page), a sessions chart with consistent totals, a key page with every expiration reported, Gateway usage with the day's requests and errors both known; anything less is named in `sourcesMissing` (the same gaps the Inbox shows). A product attempt that established nothing (every source failed, or the read never reached the service) is kept as the latest failed attempt beside the product's last outcome that did, which stays shown as older; the read is failed while such an attempt is the latest (a missing role is a settled attempt reported on the product, not a failed read). Once anything was attempted, every chosen source nothing has reached yet is named as unread coverage too, and `settledAt` carries the time of the latest attempt so a completion that established nothing is announced for when it settled, never as a first read still pending. A healthy empty read older than the ten-minute window (`OverviewView.fresh`, C12) is a gap: Home and the Inbox keep the cached read and name its age instead of an all-clear, never re-reading on their own; a refresh in progress keeps that read and its age named until the new read lands (admission restores nothing). A chosen Gateway with no workspace is unread coverage, named in `sourcesMissing`; `recheckProduct` re-reads one chosen product. The read completes (one generation) when every part admitted under the tenant's current context has landed; a read in which no source answered is a failed read (`failed`, with `failedAt`), never pending and never done, and a failed refresh keeps the earlier read labelled as older | No second read pipeline, and Home never claims coverage a read did not establish (I4): revised after the C30 attempt-01 review, which found selected Red Team and model/skill products left unread and a workspace-less Gateway announced as complete |
| P34 | Inbox items with `kind`, `severity` and `explanation` per item | `InboxEntry` carries the overview item (Runtime, Gateway) or the C29 setup warning with its hold (listed, with every action, whatever the read status: a warning exists before any read); the explanation is per kind in the presentation's copy, not invented per item; `deadline` is absent (P20). Its action carries an `InboxTarget` (destination, product, Administration inventory, item name): a key item opens Administration on the API keys inventory filtered to the key, a setup warning opens where it is fixed (Settings for the scan key or management client, AI Gateway, AI Red Teaming) | The admitted reads report no per-item explanation or deadline; the target was added after the attempt-01 review found actions landing on the destination's default view |
| P35 | Guard offers "Archive and switch" / "Discard and switch" | Archive ends the conversation (its protected history stays as C20 saved it); Discard ends it, removes its protected history record (after any save under way, under the same lock the sink holds) and refuses every later save of it (the turn the stop cuts short), then drops it once its task returns; both then switch once; the pending approval is never decided for the operator; the dialog's initial focus is Stay, the safe default (Enter on arrival ends nothing). A save admitted before the discard (the turn the engine's end cut short) re-checks the tombstone under the history hold before it writes, so it can never write the discarded transcript back after the removal. A removal that fails (storage unavailable, access denied) is never implied to have succeeded: the record stays listed and the workspace's history reports the failure, through unrelated opens and removals, until the operator removes the record | The engine is stopped either way: a switch retires its binding (C20); the difference is whether the transcript is kept, which the dialog promises and the attempt-01 review found unkept |
| P36 | Completing "Add a tenant" switches to the new tenant | `completeTenantSetup{resolution?}` goes through the same guard as `selectTenant`: a pending Harness decision refuses it with `switchBlocked{to: <draft id>, completion: true}`, nothing is committed or retired, the draft stays, and the wizard renders the one guard dialog and re-sends the completion with the resolution | Wizard completion is listed among the entry points of the single guarded switch path (shell.md, I1); the attempt-01 review found it bypassing the guard |
| P37 | Scopes are per tenant and a switch round trip shows the cached state | Each opened tenant owns its read record in the core (its last overview, the other products' outcomes, generation, recheck, snooze receipt) for the session; a switch away and back shows it again without a new read. Per-operation bookkeeping is separate from the cached data: each read part is tracked with the context it was admitted under, "reading" means a part under the current context is open, a part under a retired context is withdrawn when it lands (never recorded, never counted), so a read held open across a switch round trip can never leave the tenant reading. The presentation's own transient state follows the tenant too: the shell store carries the shown scope (set from each snapshot before it renders); a toast for a tenant's item or read and an unconfirmed delivery bound to a context are refused at insertion when that scope is no longer shown (a refusal or lost delivery arriving after a switch), retired on leaving it (however long Reduce Motion would keep them) and filtered at render; a contextual arrival belongs to the tenant it was followed in | I2 names the tenant, not the context, as the owner of its cached scopes; the attempt-01 review found the overview bound to the context and lost across A → B → A |
| P38 | Snooze toast states the core-computed return time | The core issues a `SnoozeReceipt{id, title, returnsAt, sequence}` on the tenant's Inbox scope for the last snooze placed in the session; the shell announces a new sequence once, in the tenant it was placed in, and never a hold a switch or a reread merely rediscovers; a snooze ends at its return time whether or not its entry is actionable, and the core's deadline ticker publishes the expiry (the holds in effect are part of the overview's time signature) | I11 wants one source for the return time and one announcement per snooze; diffing holds between snapshots announced old holds after a switch (attempt-01 review) |
